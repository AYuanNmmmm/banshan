# 「搬山」架构对标分析：与开源网盘迁移工具对比

> 调研时间：2026-10-25
> 对标对象：rclone、Alist、Cloudreve、b2a / Quark2Baidu 等同类迁移工具

---

## 一、对标项目的架构核心

### 1. rclone（云存储同步标杆，Go）

最有价值的三点设计：

| 设计 | 说明 |
|---|---|
| **能力协商 + 优雅降级** | 后端用 Feature Flags 声明自己支持什么（`server-side copy`/`DirMove`/`MultithreadUpload`…），核心逻辑据此降级：不支持服务端复制就退回"下载再上传" |
| **三阶段流水线** | `扫描 backlog` → `checkers`（并发判等，默认 8）→ `transfers`（并发传输）。判等和传输解耦，大量文件时判等不被串行拖慢 |
| **原子写入** | 默认写 `.partial` 临时文件，完成后原子重命名；失败删临时文件。对外永远看不到半成品 |

其他值得注意：两级重试（low-level 单请求 / high-level 整操作）、`--bwlimit` 时间表、内存上界公式 `transfers × chunk-size × streams`。

### 2. Alist（60+ 网盘聚合，Go）

**组合式接口**是它最关键的设计：

```go
type Driver interface {
    Meta      // 必须：Config / Init / Drop / GetStorage
    Reader    // 必须：List / Link
    // 以下是可选，按能力实现
}
type Getter  interface { Get() }        // 可选
type Mkdir   interface { MakeDir() }    // 可选
type Move    interface { Move() }       // 可选
type Put     interface { Put() }        // 可选
type Remove  interface { Remove() }     // 可选
```

调用方用类型断言检测能力：`if w, ok := drv.(driver.Writer); ok { ... }`

> 好处：只读网盘只写 4 个方法就能接入；能力缺失是**编译期/装配期**可知的，不是运行时炸。

另外它有**三种传输模式**：302 直链（不耗流量）、代理 URL、本机中转（兼容性最好）。我们是本机中转，属于最稳的那档。

### 3. Cloudreve（自建网盘，Go）

统一的上传协议抽象：
```
create session → {session_id, chunk_size, upload_urls[], expires}
upload chunks（chunk_concurrency 并行，走预签名 URL 直传）
complete（按存储类型：本地/OSS CompleteMultipartUpload…）
```
要点：**分片大小由会话下发**，客户端不猜；**并发数由存储策略下发**，不是全局写死。

### 4. b2a / Quark2Baidu（Python 同类工具）

- b2a：**先下载到本地再上传**（落盘），`-s` 才保留本地文件；断点续传靠 aigpy 框架
- Quark2Baidu：只有秒传转存，不落地大文件
- 共同点：CLI/TUI，无自动化测试，错误处理基本是 `try/except + print`

## 三、我们**做得比开源项目好**的地方（不要改坏）

这几条是真实优势，优化时不能丢掉：

1. **流式转发不落盘**：b2a 要先把文件下到本地再传，我们直接"边下边传"。省一倍磁盘，也省一半时间。
2. **分片级断点续传**：`done_parts` 落库，重启后问服务端哪些片已经收下。b2a 依赖通用框架，跨进程续传做不到这么细。
3. **按网盘能力收敛档位**（刚做的）：`min(档位设置, 源端 read_max, 目标端 upload, 源端 conn)`。rclone 有类似思路，但国内这些网盘的"4MB Range 上限""固定分片"这种坑，开源项目里没人系统处理过。
4. **137 个自动化测试**：这是碾压同类的。Alist/rclone 有测试但都是 Go 的，Python 迁移工具里几乎没有。

## 四、真实差距与优化建议

### P0：扫描阶段的能力预检（收益最大，改动最小）

**现状问题**：0 字节文件是**运行时**才发现不支持 ——

```
ads/baidu.py:561   if size <= 0: raise BaiduError("不支持 0 字节文件")
ads/quark.py:316   if size <= 0: raise QuarkError(...)
ads/tianyi.py:420  if size <= 0: raise TianyiError(...)
```

后果：用户扫 1000 个文件，50 个是 0 字节 → 开始迁移后这 50 个**每个都重试 3 次**（2s+4s+8s），才标 failed。白等几分钟，日志全是噪音。

**改法**（借 Alist 的能力标志思路）：给 SinkAdapter 加能力声明，扫描时预检：

```python
class SinkAdapter:
    supports_empty_file = True      # 百度/夸克/天翼改为 False
    max_name_bytes = 255            # 夸克实测 255 字符截断

# engine.scan() 里，写入任务库前
if entry["size"] == 0 and not self.sink.supports_empty_file:
    entry["skip"] = True
    entry["skip_reason"] = "目标网盘不支持 0 字节文件"
```

收益：扫描完就能告诉用户"其中 50 个将跳过（目标盘不支持空文件）"，而不是传到最后才失败。

---

### P0：错误分类，别把所有错都重试 3 次

**现状问题**：`engine._process` 里所有异常一律重试 `retries` 次：

```python
except Exception as exc:
    ...
    if round_no >= retries:
        self.db.update(task_id, state="failed", error=message)
```

但"天翼未登录"这种错误重试 100 次也没用 —— 实际日志里就是：

```
重试 1/3：... 还没登录天翼云盘（2s 后）
重试 2/3：... 还没登录天翼云盘（4s 后）
重试 3/3：... 还没登录天翼云盘（8s 后）
失败：... 还没登录天翼云盘
```

**改法**：给异常加 `retryable` 标记（rclone 就是两级重试）：

```python
class AdapterError(Exception):
    retryable = True          # 默认可重试（网络抖动等）

class AuthError(AdapterError):
    retryable = False         # 未登录/令牌失效 → 立即失败，提示用户登录

# engine._process
if not getattr(exc, "retryable", True):
    self.db.update(task_id, state="failed", error=message)
    self.log(f"失败（需人工处理）：{rel} —— {message}", "error")
    return
```

更进一步：未登录应该**中断整轮**（后面所有文件都会同样失败），而不是逐个失败。

### P1：分片内的字节进度不持久化

**现状**：`done_parts` 记到分片级。一个 10MB 分片传到 9MB 时进程退出，重启要**从 0 重传这 10MB**。

会员 8MB/s 时影响小（1.2 秒），但非会员 100KB/s 时是 100 秒的浪费。

**改法**（成本中等）：任务库加 `part_progress_json = {"3": 9437184}`（第 3 片已读 9MB），重启后 `read_range(offset + 已读, 剩余)`。

**建议**：会员用户可以不急，非会员场景价值大。

---

### P1：server.py 拆分成多个 service

**现状**：`App` 类 45 个方法，横跨 12 类职责（登录/OAuth/天翼浏览器/挑选/任务/扫描/浏览/配置/容量/调度/demo/CSV 导出）。

**问题**：改任何一块都要动同一个类，137 个测试里一半要构造整个 App。

**改法**（渐进式，不一次性重构）：

```
server.py          只留 HTTP 路由 + dispatch（约 200 行）
app/context.py     AppContext：cfg / db / engine / adapters 的装配与共享
app/auth.py        扫码 + OAuth + 天翼一键登录（含 _find_edge/_find_node）
app/picker.py      pick_files / pick_paths / _expand_dir / _resolve_path
app/tasks.py       remove / retry / select / report_csv
app/state.py       state / scan_status / quota
```

按依赖顺序拆，每拆一块跑一次全量测试。风险可控但耗时。

### P2：前端模块化

**现状**：`app.js` 1419 行、59 个顶层函数、8 个全局状态（`S`/`browse`/`view`/`builtFor`/`sigTasks`/`sigLogs`/`scanPolling`/`tyloginPolling`）。

**改法**（优先级低于后端）：至少拆成 ES module：

```
web/js/api.js       fetch 封装 + 错误统一
web/js/state.js     S / providers 的读写 + 订阅
web/js/panels.js    两端面板渲染
web/js/browse.js    目录浏览对话框
web/js/tasks.js     文件明细表
web/js/settings.js  档位与高级设置
web/js/app.js       入口，只做装配
```

---

### P2：UI 缺「当前在传什么」

**现状**：7 个统计格 + 一条全局进度条 + 文件明细表。但**看不到"此刻正在传哪个文件的第几片"**。

非会员慢速时（一个 10MB 片要 100 秒），进度条几乎不动，用户会怀疑卡死（这次踩过）。

**改法**（小改动，收益直观）：

- 在 `#prog-right` 旁边加一行：`正在传：xxx.mp4 第 5/33 片`
- 文件明细里 running 那行显示 `done_parts/total_parts`
- 数据都已有（`engine.snapshot` 里有 tasks 的 `done_parts`/`total_parts`），只是没渲染

---

### P2：缺少「计划预览」（dry-run）

rclone 有 `--dry-run`。我们点"开始迁移"前，用户不知道：

- 会传多少文件/字节
- 有多少会跳过（已存在 / 0 字节 / 不支持）
- 预计多久（按当前速度估算）
- 目标盘空间够不够（已有 quota，但没有前置阻断）

**改法**：扫描完成后弹一个确认卡片：
```
将迁移 128 个文件（3.2GB）
  跳过 12 个（目标已存在 10，空文件 2）
  目标剩余 1.5TB，足够
  按当前网络预计 6 分 40 秒
[开始] [取消]
```

## 五、不建议动的（避免过度设计）

| 想法 | 为什么不建议 |
|---|---|
| 照搬 rclone 的 `checkers` 并发判等 | 我们是内存 dict 比对（`existing.get(rel)`），比 HTTP 判等快几个数量级，加并发纯属浪费 |
| 学 Cloudreve 的「会话下发分片大小」 | 我们的分片大小由**目标网盘硬性规定**（百度 4MB/天翼 10MB），不是我们自己能定的 |
| 搞秒传 | 跨厂商迁移时目标盘没有源文件，命中率≈0（已论证过） |
| 上 asyncio / 线程池重写 | 当前 ThreadPoolExecutor + 信号量已够，重写收益不抵风险 |
| 引入 ORM / Web 框架 | 纯标准库是这个项目的核心卖点（零依赖打包 18MB），不要丢 |

---

## 六、建议的执行顺序

如果只做三件事：

1. **P0 能力预检**（半天）—— 扫描时就标出 0 字节等不支持的文件，省掉几分钟白等
2. **P0 错误分类**（半天）—— 未登录/权限问题立即失败并提示，不要重试 3 次
3. **P2 UI 显示当前分片**（2 小时）—— 数据都有，只是没渲染，慢速时体感差别巨大

架构拆分（P1）和前端模块化（P2）属于"长期健康度"，不紧急，可以等下次做大功能时顺手做。
